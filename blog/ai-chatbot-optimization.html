Optimizing RAG Systems for Fast Response Times

February 22, 2025

When building PDFgpt, an iOS app that lets users chat with their PDF documents, one of the biggest challenges was achieving fast response times for the RAG (Retrieval-Augmented Generation) system. Users expect near-instant responses, especially on mobile devices, but traditional RAG implementations can be slow due to multiple API calls and processing steps.

The RAG Performance Challenge

A typical RAG system involves several steps:

  1. User submits a question
  2. Query is embedded using an embedding model
  3. Vector similarity search finds relevant document chunks
  4. Retrieved context is combined with the query
  5. Large language model generates a response

Each step introduces latency, and when you're making API calls to external services, these delays can quickly add up to response times of 10+ seconds, which is unacceptable for a smooth user experience.

Our Optimization Strategy

To achieve sub-3-second response times, we implemented several key optimizations:

1. Embedding Caching and Pre-computation

Instead of computing embeddings for every query in real-time, we:

  • Pre-computed document embeddings: When a PDF is uploaded, we immediately chunk and embed all content
  • Query embedding caching: Common queries and their embeddings are cached locally
  • Batch processing: Multiple chunks are embedded together to reduce API overhead

2. Smart Vector Database Design

We chose ChromaDB for local vector storage and optimized it for mobile performance:

  • Hierarchical indexing: Documents are organized in a hierarchy to reduce search space
  • Lazy loading: Only load embeddings for the current document into memory
  • Approximate search: Use HNSW indexing for faster similarity search with minimal accuracy loss

3. Parallel Processing Pipeline

We redesigned the RAG pipeline to process steps in parallel where possible:

  • Concurrent retrieval: While embedding the query, we prepare the vector database for search
  • Streaming responses: Start processing the LLM response as soon as we have context, don't wait for full retrieval
  • Background preloading: Predict likely follow-up queries and preload relevant context

4. Local vs. Remote Processing

One of the biggest performance wins came from running parts of the pipeline locally on the device:

  • Local embeddings: Used a quantized version of sentence-transformers running on CoreML
  • Vector search: All similarity search happens locally, eliminating network latency
  • Context preparation: Chunk ranking and context assembly happen on-device

Implementation Details

CoreML Integration

Getting a transformer model running efficiently on iOS required several optimizations:

  • Model quantization: Reduced the embedding model from 32-bit to 8-bit weights
  • Input optimization: Preprocessed text to minimize tokenization overhead
  • Batch processing: Process multiple text chunks simultaneously when possible

Memory Management

iOS apps have strict memory constraints, so we implemented careful memory management:

  • Chunked loading: Load document embeddings in chunks rather than all at once
  • LRU caching: Cache frequently accessed embeddings with automatic eviction
  • Memory pressure handling: Clear caches and reduce precision under memory pressure

Performance Results

Our optimizations achieved significant performance improvements:

  • Response time: Reduced from 12+ seconds to 2.8 seconds average
  • First token: Streaming responses start in under 1 second
  • Offline capability: Basic functionality works without internet connection
  • Battery life: 40% reduction in energy consumption per query

Lessons Learned

1. Network Latency is the Biggest Bottleneck

API calls to external services dominated our initial response times. Moving computation local eliminated the most significant performance bottleneck.

2. User Perception Matters

Streaming responses and showing partial results immediately made the app feel much faster, even when total processing time was similar.

3. Mobile-First Design is Different

Optimizations that work well on servers (like large batch sizes) don't always translate to mobile devices with limited memory and battery life.

4. Quality vs. Speed Trade-offs

We found that slight reductions in embedding quality (through quantization) were acceptable if they enabled significantly faster responses.

Future Improvements

There are several areas where we could further optimize the system:

  • Predictive caching: Use user behavior patterns to predict and preload likely queries
  • Progressive enhancement: Start with fast, lower-quality responses and refine them in the background
  • Hardware acceleration: Leverage Neural Engine on newer iOS devices for faster inference
  • Adaptive quality: Automatically adjust processing quality based on device capabilities and battery level

Conclusion

Building a fast RAG system for mobile devices requires rethinking traditional server-side architectures. By moving computation to the edge, implementing smart caching strategies, and optimizing for mobile constraints, we were able to create a responsive PDF chat experience that users love.

The key is to remember that performance optimization is not just about making things faster—it's about creating a better user experience that feels instant and effortless.
